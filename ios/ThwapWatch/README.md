# Thwap for Apple Watch (scaffold)

A standalone watchOS app plus a WidgetKit complication. It talks to https://thwaphockey.com through `LiveThwapAPI` (design doc `docs/apple-watch-design.md`, sections 5, 6, 8 and 9). `StubThwapAPI` stays for previews, UI tests and screenshots.

## How it ships

The watch app has its own project, `ios/ThwapWatch/ThwapWatch.xcodeproj`, generated by XcodeGen. The iPhone app ships it. One archive of the iPhone app carries the watch app, so one App Store listing and one TestFlight build cover both.

How the two projects connect:

- `ios/App/App.xcworkspace` lists `ThwapWatch.xcodeproj` next to `App.xcodeproj`.
- `App.xcodeproj` references `ThwapWatch.xcodeproj` as a subproject.
- The `App` target depends on the `ThwapWatch` target, so building App builds the watch app first.
- The `App` target has an `Embed Watch Content` phase. It copies the watch app (`Thwap.app`, with the complication inside it) to `App.app/Watch`.

The watch targets stay in their own project on purpose. `npx cap sync` and `pod install` rewrite `App.xcodeproj`, and the watch project is regenerated by XcodeGen. Keeping them apart means neither tool edits the other's targets. Both tools were checked: `npx cap sync ios` (which runs `pod install`) leaves the embed in place.

`ios/scripts/embed-watch.rb` adds the embed and is safe to run again. Run it if the embed ever goes missing, for example after recreating the Capacitor iOS project. It also stops with an error when the watch app and the iPhone app have different version or build numbers.

```sh
cd ios && ruby scripts/embed-watch.rb
```

It needs the `xcodeproj` gem, which comes with CocoaPods. With Homebrew CocoaPods, point Ruby at it: `GEM_PATH=$(brew --prefix cocoapods)/libexec ruby scripts/embed-watch.rb`.

The watch app still runs on its own (`WKApplication`, `WKRunsIndependentlyOfCompanionApp = YES`). A kid does not need the iPhone app open to use it.

### Versions

The watch app's version and build number must match the iPhone app's. App Store Connect rejects the upload otherwise. When you bump `MARKETING_VERSION` or `CURRENT_PROJECT_VERSION` on the App target, set the same values in `project.yml`, then run `xcodegen generate`.

### Archive and upload (owner steps)

1. Register the App Group `group.com.thwaphockey.app` on the Apple Developer account. Turn it on for `com.thwaphockey.app.watchkitapp` and `com.thwaphockey.app.watchkitapp.rings`.
2. Open `ios/App/App.xcworkspace` in Xcode. Always open the workspace, not a single project.
3. Set your team under Signing & Capabilities on three targets: `App` (App project), `ThwapWatch` and `ThwapComplication` (ThwapWatch project). Every target uses Automatic signing, so the team is all you need to set.
4. Pick the `App` scheme and `Any iOS Device (arm64)`.
5. Choose Product > Archive.
6. In the Organizer, check the archive shows as an iOS App. Then choose Distribute App > App Store Connect > Upload.
7. In TestFlight, install the iPhone build. The watch app then shows up in the Watch app on the iPhone, under Available Apps. It can also be installed from the App Store on the watch.

To regenerate the watch project after editing `project.yml`:

```sh
brew install xcodegen   # once
cd ios/ThwapWatch && xcodegen generate
```

Do not edit `ThwapWatch.xcodeproj` by hand. Keep the target name `ThwapWatch`: the App project points at it by XcodeGen's stable target id.

## Layout

| Path | What |
|---|---|
| `ThwapCore/` | Swift package with the pure logic: wire models that mirror the server JSON, the `ThwapAPI` protocol, `LiveThwapAPI` (URLSession behind an injectable `HTTPTransport`), `KeychainTokenStore`, `ApprovalPoller`, `StubThwapAPI` fixtures, `CheckOffQueue`, `RingMath`, `DrillTimer`, `RingStore` (App Group). No UI. |
| `WatchApp/` | SwiftUI screens: Sign in, Ask a parent (waiting), Today (with undo confirm and sign out), drill running, THWAP stamp, Game Day Goals, My Season, Team. Plus `Haptics`. |
| `Complication/` | WidgetKit complication: circular (3 concentric rings) and rectangular. |
| `Shared/` | Theme tokens and the ring view, compiled into both the app and the complication. |

Bundle ids: `com.thwaphockey.app.watchkitapp` (app), `.watchkitapp.rings`, `.watchkitapp.tests`. App Group: `group.com.thwaphockey.app`. The App Group needs registering on the Apple Developer account before a device build will sign.

## Content source

Drill names, cues and timings come from `index.html` (`DRILLS`, `SHOOT_DAYS` day 1, `WORKOUTS` w1wed, `THWAP_DRILL_SCRIPT`). Work seconds are reps x perRep x sides, or shots x everySeconds for callout drills, or rounds x restSeconds x sides for rounds drills. Game goals come from `hockey_game_goals.html` and the game from `lib/schedule_store.js`. The player is a placeholder ("Demo"), not a roster kid.

## Haptics

| Moment | `WKHapticType` |
|---|---|
| Timer starts | `.start` |
| Any set ends | `.notification` (strongest, felt mid-rep) |
| Check-off stamp | `.success` (reads as "got it", kept for the stamp only) |

The simulator plays no haptics. Judge these on a real watch.

## Talking to the server

| Call | Endpoint | Notes |
|---|---|---|
| Sign in | `POST /api/login?action=watch-request { teamCode, code, deviceLabel }` | `code` is the player code. 401 is a wrong code (never clears a token). 429 shows "Too many tries." |
| Wait for a parent | `GET /api/login?action=watch-status&requestId=` | `ApprovalPoller`: every 3 s for the first minute, then backs off to every 10 s, gives up at 15 minutes (the server request lifetime). Network errors back off and keep waiting. `approved` stores the token once; `denied` and `expired` end the wait. |
| Session check | `GET /api/login?action=session` | Once per launch. `authed: false` signs out. |
| Today | `GET /api/done?view=today` + `GET /api/done` | The server list wins; this watch's unsent taps are laid on top. |
| Game Day Goals | `GET /api/coach?action=my-game-goals` | Shown only when `gameDay` is true. A failure hides the goals and never blocks the drill list. |
| Check off / undo | `POST /api/done` via `CheckOffQueue` | Flushed on launch, on foreground and after every tap. |
| My Season | `GET /api/done?view=season` | The scene the kid is in and the training days to the next one, from `lib/journey.js` (the journey page's math). Read after the drill list; a failure only shows "No signal" on that screen. |
| Team | `GET /api/done?view=team` | This week's team goal, total and to go (the Standings bar numbers), plus the kid's own share. No list of kids. Same failure rule. |
| Rings | `GET /api/done?view=rings` | This week's done/goal, written to the App Group, then `WidgetCenter.reloadAllTimelines()`. A check-off bumps the ring straight away. |
| Sign out | `POST /api/login?action=logout` | Then clears the Keychain item, the queue and the rings. Warns first when drills have not synced. |

The token sits in the Keychain (generic password, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, never synced) together with the player it belongs to. Every signed-in call sends it as `Cookie: thwapSession=<token>`; URLSession's cookie jar is off, so the Keychain is the only source. Any 401 on a signed-in call clears it and returns to sign-in. The queue is kept, so it all goes once a parent approves again.

Queue rules: offline, 5xx, 429 and 401 keep the entry and stop the flush so order is kept. 400 and 402 (season not active) and 403 drop it. An entry leaves only on a 2xx or a drop. A mark from an earlier day carries its `date`; today's mark lets the server's clock decide. An undo of an unsent mark just cancels it locally; an undo whose day has passed is dropped (the server undo is today only). Queue files from the scaffold (version 1, marks only) still load.

Base URL: `https://thwaphockey.com`, overridable with `-thwapBaseURL <https url>` or an Info.plist `ThwapBaseURL` key.

## Build and test

```sh
cd ios/ThwapWatch
# Ad-hoc signed, so the Keychain test can run (an unsigned build has no
# Keychain entitlement, and that one test skips itself):
xcodebuild -project ThwapWatch.xcodeproj -scheme ThwapWatch \
  -destination 'platform=watchOS Simulator,name=Apple Watch Series 11 (46mm)' \
  CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual test
# logic only, on the Mac:
cd ThwapCore && swift test
```

Check the embed without signing (from the repo root, after `npm install` and `npx cap sync ios`):

```sh
xcodebuild -workspace ios/App/App.xcworkspace -scheme App -configuration Release \
  -destination 'generic/platform=iOS' -archivePath /tmp/App.xcarchive \
  archive CODE_SIGNING_ALLOWED=NO
ls /tmp/App.xcarchive/Products/Applications/App.app/Watch/Thwap.app/PlugIns
```

Endpoint tests replay JSON fixtures in `ThwapCore/Tests/ThwapCoreTests/Fixtures/`, captured from the server handlers. They are read from the source tree via `#filePath`, not bundled.

Launch arguments (stub data, no network): `-thwapStub`, `-thwapScreen signin|waiting|denied|expired|today|run|stamp|goals|season|team` (implies `-thwapStub`), `-thwapGameDay`, `-thwapElapsed <seconds>`. Without them the app uses the real client.

## Only checkable live

- The parent email, the Approve page and token pickup end to end.
- That watch-request takes `{ teamCode, code, deviceLabel }` and my-game-goals takes the watch token (parallel server change).
- Keychain and App Group on a signed device build (the App Group needs registering on the developer account).
- The complication refresh after a check-off, and haptics.
